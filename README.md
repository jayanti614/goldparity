## What Phase 2 + 3 actually do

**Phase 2 (`app/analytics/fair_value.py`)** converts every contract's quoted
price into a purity-adjusted, per-gram, "999-equivalent" fair value — the
common basis every contract can finally be compared on.

**Phase 3 (`app/analytics/decomposition.py` + `detection.py`)**:
1. Estimates each contract's own implied daily carry rate from its own
   front-month vs next-month price (no external assumptions needed).
2. Roll-down-adjusts every contract to a common reference expiry day —
   if a contract has no next-month data to estimate carry from, it is
   deliberately left unadjusted rather than guessed (see
   `test_symbol_with_no_next_month_gets_no_roll_down_adjustment`).
3. Compares the adjusted prices to produce a `residual_signal_pct` per
   contract — what's left over after removing purity and roll-down effects.
4. `detection.py` flags a residual as statistically unusual only when it's
   an outlier against that *same contract's own* trailing 20-day history
   (z-score ≥ 2), computed look-ahead-safe so Phase 4's backtest can reuse
   these flags honestly.

Ran against your real uploaded file (18 Sep 2026): after normalization,
**GOLDTEN came out 0.115% cheap relative to the other three contracts** —
a real decomposed signal on real data, not synthetic noise.

## What Phase 4 + 5 actually do

**Phase 4 (`app/analytics/backtest.py`)** replays every flagged signal as a
hypothetical relative-value trade: enter the next trading day after a flag
(never the flag day itself — that would be lookahead), hold for a fixed
5-day period, measure the return as the change in residual over that
window, subtract realistic round-trip costs (4 leg-executions × a
configurable per-leg cost). Then it bootstrap-resamples the completed
trades' net returns to get a confidence interval on the average trade
return — and says plainly when that interval spans zero, meaning no edge
survives costs at the current sample size, rather than dressing up a small
noisy sample as a strategy.

**Phase 5a (`app/analytics/carry.py`)** fits a line through every available
(days-to-expiry, log price) point across all 4 contracts' curves that day
and reports the slope as a single implied annualized carry rate, along
with an R² so the number carries its own honesty check.

**Phase 5b (`app/analytics/delivery_risk.py`)** excludes any trade that
would still be open once its contract enters MCX's staggered-delivery
tender window — verified against real broker circulars (all 4 gold
contracts are compulsory-delivery; the tender window opens a few days
before expiry). This is a correction of an earlier, less accurate claim
made mid-project (originally described as "3 of 4 contracts, no fresh
positions on expiry day only" — the checked, real version is broader and
starts earlier than that).

**A bug the tests caught along the way:** the first version of Phase 3's
`reference_price` averaged all 4 contracts' prices *including the one
being evaluated*, which mechanically dampens and biases its own measured
deviation. Fixed to a leave-one-out reference (a contract's benchmark is
always the mean of the *other* contracts only) — standard relative-value
practice. This changed the backtest's headline result: before the fix, the
same 13 trades showed a statistically significant *negative* return; after
the fix, the honest result is "no significant edge at this sample size,"
which is what you'd expect from 13 trades where only one had a genuinely
engineered mispricing. Real historical MCX data across a much longer
window is what will actually answer whether there's a persistent edge —
this backtest engine is what will test it once that data is loaded.

## What Phase 6 + 7 actually do

**Phase 6 (`app/main.py` + `app/api/`)** wraps everything built in Phases
1-5 in a FastAPI REST layer: `/api/status`, `/api/contracts`,
`/api/signals/latest`, `/api/signals/history/{symbol}`,
`/api/signals/flagged`, `/api/backtest`, `/api/carry/history`. It also adds
one new piece of analysis — the **Arbitrage Score** (`app/analytics/arbitrage_score.py`):
a 0-100 gauge that is deliberately *not* an arbitrary fixed scale. It's the
percentile rank of today's cross-contract spread within this market's own
historical spread distribution, so "83" means something real: today's
mispricing is wider than 83% of days in the loaded history.

**Phase 7 (`frontend/`)** is a Vite + React dashboard — light theme, a
gold/ink palette grounded in the subject matter rather than generic
SaaS styling, tabular/monospace numerics throughout. It shows the live
arbitrage score gauge, a contract ticker, the signal decomposition chart,
residual history per contract (with flagged days marked), the full
backtest trade log with its bootstrap verdict, the implied carry chart,
a roadmap grid distinguishing what's live from what's planned for the
Manali build (clicking a planned feature opens a modal — nothing is
silently missing), and an About section that pulls its "N of 9 phases
built" line live from the API rather than being hardcoded.

Both were run and screenshotted end-to-end against real data before
being shipped, including clicking through a "planned feature" modal to
confirm it behaves the way it was asked to.

## Running the full stack (two Command Prompt windows)

**Window 1 — backend:**
```
cd backend
venv\Scripts\activate
python scripts\generate_sample_data.py
python scripts\run_pipeline.py
python scripts\run_analytics.py
python scripts\run_backtest.py
uvicorn app.main:app --reload
```
Leave this running. Check http://127.0.0.1:8000/docs loads.

**Window 2 — frontend** (first time only, install Node.js from
nodejs.org if `node --version` doesn't work):
```
cd frontend
npm install
npm run dev
```
Open the URL it prints (http://localhost:5173/). The dashboard should
load live data from the backend automatically.

## Phase 9 — Deploying this for real

Right now this only runs on your own laptop. Deploying puts it on the
internet with a real link anyone (including judges) can open — no
Python or Node install required on their end.

**The plan:** the backend (FastAPI) goes on **Render** (free tier), the
frontend (React) goes on **Vercel** (free tier). Both connect directly to
your GitHub repo, so every future `git push` can redeploy automatically.

### Step 1 — Deploy the backend on Render

1. Go to render.com and sign up/log in (using your GitHub account is easiest).
2. Click **New +** → **Web Service**.
3. Connect your GitHub account if asked, then select your `GoldParity` repo.
4. Fill in these settings:
   - **Root Directory:** `backend`
   - **Runtime:** Python 3
   - **Build Command:**
     ```
     pip install -r requirements.txt && python scripts/generate_sample_data.py && python scripts/run_pipeline.py && python scripts/run_analytics.py && python scripts/run_backtest.py
     ```
   - **Start Command:**
     ```
     uvicorn app.main:app --host 0.0.0.0 --port $PORT
     ```
   - **Instance Type:** Free
5. Click **Create Web Service**. It'll take a few minutes the first time.
6. Once it's live, copy the URL Render gives you (something like
   `https://goldparity-api.onrender.com`). Check `https://<that-url>/docs`
   loads.

*Note: the free tier sleeps after 15 minutes of no traffic. The first
visit after that will take ~30-60 seconds to wake up — normal, not a bug.*

### Step 2 — Deploy the frontend on Vercel

1. Go to vercel.com and sign up/log in with GitHub.
2. Click **Add New** → **Project**, and import your `GoldParity` repo.
3. Set **Root Directory** to `frontend`. Vercel should auto-detect Vite.
4. Before deploying, add an environment variable:
   - **Name:** `VITE_API_BASE_URL`
   - **Value:** your Render URL + `/api`, e.g. `https://goldparity-api.onrender.com/api`
5. Click **Deploy**.
6. Once done, Vercel gives you a URL like `https://goldparity.vercel.app` —
   open it and confirm the dashboard loads real data.

### Step 3 — Let the backend trust the frontend's real domain

1. Back in Render, open your service → **Environment**.
2. Add an environment variable:
   - **Name:** `ALLOWED_ORIGINS`
   - **Value:** your Vercel URL, e.g. `https://goldparity.vercel.app`
3. Save — Render will redeploy automatically.
4. Reload your Vercel URL and confirm the dashboard still loads data (this
   step is what makes the browser's CORS check pass in production).

From here on, any `git push` to your repo auto-redeploys both sides.

## Using a real MCX file

1. Download a CSV from https://www.mcxindia.com/market-data/bhavcopy by hand.
2. Put it in any folder.
3. `python scripts\run_pipeline.py --dir path\to\that\folder`

If the columns don't match what the parser expects, it will tell you exactly
which column it couldn't find — send that to Claude and we'll fix
`_HEADER_ALIASES` in `parser.py` to match.
